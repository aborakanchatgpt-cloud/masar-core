# RUNBOOK.md — دليل تشغيل "مسار" اليومي (لأحمد)

هذا الدليل لك أنت، لا للعميل. لغته تقنية ومباشرة. الهدف: تعرف ماذا تفعل يوميًا، وماذا تفعل عند أي عطل، بلا حاجة للرجوع لكود المصدر كل مرة.

## 0. الوصول السريع

- **الخادم:** `masar-core-1` (Hetzner، IP `62.238.117.20`) — `https://62.238.117.20.sslip.io`.
- **كل الأوامر أدناه عبر `Core - Call` (n8n) أو جسر MCP** — لا SSH مطلوب لأي عملية يومية اعتيادية. صيغة الاستدعاء: `{"path": "...", "method": "GET|POST", "body": {...}}`.
- **التوكن:** `CORE_ADMIN_TOKEN` — محفوظ في اعتماد n8n "Masar Core Admin Token"، وفي `.env` على الخادم. لا تكتبه في أي محادثة.
- **SSH حقيقي** (فقط عند العجز عبر القنوات أعلاه): إن كان لديك مفتاح الخادم محفوظًا محليًا.

## 1. القراءة اليومية — `/admin/overview`

استدعِ `GET /admin/overview` كل صباح (أو أي وقت تريد لمحة سريعة). يرجع:

| الحقل | ماذا يعني | متى تقلق |
|---|---|---|
| `customers_by_status` | عدد العملاء لكل حالة (active/paused/expired) | تراجع مفاجئ بـ`active` |
| `sends_today` / `sends_last_7_days` | عدد التقديمات المُرسَلة | `sends_today` = 0 بعد الساعة 12 ظهرًا رغم عملاء نشطين |
| `bounces_today` | عدد الرسائل المرتدة اليوم | معدّل الارتداد (bounces_today ÷ sends_today) > 3% |
| `send_queue_by_status` | حالة طابور الإرسال (queued/sent/failed...) | تراكم كبير بـ`queued` أو ارتفاع بـ`failed` |
| `mail_links_by_status` | حالة ربط بريد كل عميل | أي `broken` — يعني عميلًا لا نرسل له حاليًا |
| `pending_reports` | تقارير 19:00 لم تُسلَّم بعد | يبقى مرتفعًا بعد 21:30 بتوقيت الرياض |
| `pending_guarantees` | تعويضات ضمان بانتظار اعتمادك | أي رقم > 0 — راجع القسم 3 |
| `discovery_freshness.latest_job_discovered_at` | آخر وظيفة اكتُشفت | أقدم من عدة ساعات بيوم عمل عادي |
| `dry_run` | هل النظام في وضع تجربة (لا إرسال حقيقي) | `true` بعد أن قررت التشغيل الحي فعليًا |

## 2. تقارير 19:00

كل عميل نشط (`status='active'`) وله بريد مربوط سليم يستلم تقريرًا يوميًا على تيليجرام بين 19:00–21:30 بتوقيت الرياض (يبنيه `core/app/reports.py`، يُسلّمه وركفلو n8n `مسار - تسليم التقرير اليومي`). التقرير يحتوي: عدد تقديمات اليوم بالتفصيل (شركة/مسمى/مدينة)، تقدّم فترته الحالية بكلمات بشرية (بلا أرقام حدّية أبدًا)، قسم "استبعدنا لك"، وأزرار 👎/🎉 لكل تقديم.

**كيف تتأكد أنها وصلت:**
1. `GET /admin/overview` → `pending_reports` يجب أن يهبط لصفر بعد 21:30.
2. إن بقي مرتفعًا: تحقق أن وركفلو "تسليم التقرير اليومي" مُفعَّل بـn8n (Executions تُظهر السبب إن فشل).
3. لتشغيلها يدويًا فورًا (اختبار أو تعويض تأخير): من بوت الأدمن على تيليجرام → "▶️ شغّل التقارير الآن"، أو مباشرة عبر Core: `POST /admin/reports/run-now` (إن وُجدت — راجع `reports_api.py` لأسماء النقاط الفعلية).

## 3. تسوية الضمان (الاشتراك الشهري)

القاعدة: هدف 510 تقديمًا محتسَبًا شهريًا. عند نهاية فترة أي اشتراك:
- بلغ الهدف → يُغلق تلقائيًا بلا أي فعل منك.
- لم يبلغه، ولم يُمنح مهلة أداء بعد → تمديد يومين تلقائي، بلا أي فعل منك.
- لم يبلغه بعد التمديد → **تعويض تناسبي يُسجَّل بانتظار اعتمادك** — لا تحويل تلقائي أبدًا.

**خطوات التسوية:**
1. `GET /admin/guarantee/pending` — يرجع كل الصفوف `status='refund_pending'` (اسم العميل، العجز `shortfall`، المبلغ المحسوب `refund_amount`).
2. حوّل المبلغ للعميل يدويًا (تحويل بنكي/محفظة حسب اتفاقك معه).
3. `POST /admin/guarantee/{id}/settle` — يُعلّم الصفّ `settled`. استدعاء ثانٍ على صفّ مُسوّى أصلًا لا يفعل شيئًا (آمن، لا يكرر).

**ملاحظة مهمة:** انقطاع بريد العميل (صندوقه مفصول/معطوب) يُمدّد الفترة تلقائيًا بدل الذهاب لمرحلة التعويض — طالما البريد معطوب، لن ترى هذا العميل في `pending`. لا تتدخل يدويًا؛ فقط تابع رسالة "بريدك بحاجة لإعادة ربط" التي وصلت للعميل.

## 4. تفعيل الكتالوج والطلبات (B7)

`GET /catalog` يرجع المنتجات النشطة (اشتراك شهري، رصيد مسبق بأحجام مختلفة، سيرة مستقلة). الأسعار تظهر `null` حتى تقرر أنت السعر النهائي — لا تُعرض للعميل أي صياغة سعر قبل أن تُحدَّد فعليًا بقاعدة البيانات (`UPDATE products SET price_sar = ... WHERE code = '...'` عبر `ops psql`).

لتفعيل طلب عميل بعد أن يدفع (يدويًا، خارج النظام حاليًا — لا بوابة دفع إلكترونية بعد):

```
POST /admin/orders
{"customer_id": 123, "product_code": "SUB30"}
```

يفعّل اشتراكه (يفتح فترة 30 يومًا، يمنح رصيد 510) أو يشحن رصيده (CR100/CR300/CR510) أو يسجّل طلب سيرة مستقلة (CV1)، حسب نوع المنتج، بمعاملة واحدة آمنة. `GET /admin/orders?customer_id=123` يرجع سجل طلباته.

## 5. أونبوردنغ عميل جديد من الصفر

1. **العميل يبدأ محادثة مع بوت "مسار"** على تيليجرام (وركفلو `مسار - تسجيل عميل جديد`) → يُدخل اسمه، المدن، المجالات، يرفع سيرته، يوافق على الشروط → يُنشأ له عميل بحالة مبدئية ويصله رابط `https://62.238.117.20.sslip.io/link/<token>`.
2. **العميل يفتح الرابط** ويُنشئ صندوق Gmail جديدًا خاصًا بالخدمة (إن لم يكن أنشأه مسبقًا)، يفعّل التحقق بخطوتين، يولّد "كلمة مرور تطبيق"، ويلصقها بالصفحة. الصفحة تختبر SMTP/IMAP فعليًا وتُحفظ الكلمة مشفّرة (Fernet).
3. **أول تقديمات:** بمجرد أن يصير `mail_links.status='ok'` والعميل `status='active'`، يبدأ التخطيط اليومي والإرسال تلقائيًا وفق جدول التسخين (القسم 7 أدناه) — لا فعل إضافي منك.
4. **تحقق سريع بعد الربط:** `GET /customers/{id}` — تأكد أن `status='active'` و`mail_link_status` سليم. راقب `/admin/overview` في اليوم التالي لتتأكد أن `sends_today` يشمله.

## 6. عند الأعطال — التشخيص والتعافي

### Core لا يستجيب (`/health` يفشل أو لا يردّ)
1. لا SSH متاح؟ استخدم جسر MCP أو `Core - Call` إن كانا يعملان جزئيًا؛ إن انقطعا كليًا فهذا يعني الموصّل نفسه معطّل (راجع بند "الموصّل معطّل" أدناه).
2. مع SSH: `docker compose ps` على `/opt/masar-core` — أي حاوية `unhealthy`/متوقفة؟
3. راجع آخر سجلّ نشر: `deploy/.deploy_needed` وسجل autodeploy (`/var/log/masar-autodeploy.log` أو ما يعادله) — هل آخر commit كسر شيئًا؟
4. **الإصلاح عبر GitHub لا SSH يدوي:** أعد آخر نسخة سليمة من الملف المعطوب (commit جديد يعيد المحتوى السابق)، انتظر دورة autodeploy (≤ دقيقتين)، تحقق من `/health` مجددًا.
5. إن استمر العطل: `docker compose logs core --tail=200` (عبر ops `logs`) لقراءة الاستثناء الفعلي.

### autodeploy عالق (flock لا يتحرر)
`autodeploy.sh` محاط بقفل `flock -n` غير حاجب — إن كانت نسخة سابقة عالقة فعليًا (لا تنتهي، مثال: بناء صورة تجمّد)، ومعك جلسة طرفية متصلة بها ظهرت عالقة:
- **Ctrl+C** لإنهاء العملية الحالية إن كانت بالمقدمة (foreground) وتستجيب.
- إن كنت متصلًا بحاوية عبر `docker attach` وتريد الخروج **بلا** إيقاف الحاوية: **Ctrl+P ثم Ctrl+Q** (تسلسل الفصل القياسي لـDocker — لا تستخدم Ctrl+C هنا فقد يوقف العملية داخل الحاوية).
- بعد التحرر: تحقق أن القفل زال (`ls -la /var/lock/masar-autodeploy.lock` لا يمنع تكة جديدة)، ثم راقب أن autodeploy التالية (خلال دقيقتين) تمر بنجاح.

### جلسات Postgres عالقة (zombie)
اتصالات معلّقة تستهلك `pool_size` بلا داعٍ (مثال: بعد إعادة تشغيل غير نظيفة):
```
ops psql "SELECT pid, state, query_start, query FROM pg_stat_activity WHERE datname='masar' AND state != 'idle' ORDER BY query_start;"
```
جلسة عالقة لأكثر من ساعة بحالة `idle in transaction`: أنهها بـ`ops psql "SELECT pg_terminate_backend(<pid>);"`. إن تكررت المشكلة راجع `DB_POOL_SIZE`/`DB_STATEMENT_TIMEOUT_MS` (متغيرات بيئة، B6).

### الموصّل (n8n / جسر MCP) معطّل = Core تبدو معطّلة
تذكّر: n8n وجسر MCP طبقتا وصول فقط، لا جزءًا من منطق مسار نفسه. إن بدت "كل شيء معطّل" لكن العميل ما زال يستلم تقاريره ويصله بريد فعلي، فالعطل في طبقة الوصول لا بالخدمة. تحقق مباشرة بمتصفح: `https://62.238.117.20.sslip.io/health` — إن ردّ 200 فالخدمة سليمة والعطل بـn8n وحده (أعد تشغيل حاوية n8n عبر ops `restart`).

## 7. تشغيل الإرسال الحقيقي (إيقاف DRY_RUN) — بأمان

النظام **DRY_RUN افتراضيًا دائمًا** (`MAIL_LIVE` غير مضبوط أو `false`) — لا إرسال حقيقي لأي عميل مهما حدث حتى تُفعّله صراحة. لا تُفعّل `MAIL_LIVE=true` إلا بعد المرور بكل بند من القائمة التالية:

- [ ] **رابط Gmail حقيقي يعمل فعليًا** لصندوق واحد على الأقل — `mail_links.status='ok'` بعد اختبار SMTP/IMAP حي حقيقي، لا `skip_verify`.
- [ ] **نافذة الإرسال مفعّلة** (`pacing.py` تعمل بلا `MAIL_IGNORE_SEND_WINDOW`) — تأكد أن الإرسال يتقيّد بساعات العمل المعتمدة.
- [ ] **جدول التسخين مضبوط** لكل صندوق جديد حسب عمره منذ الربط: الأيام 1–2 → 6/يوم، 3–5 → 12/يوم، 6–9 → 16/يوم، 10+ → 20–22/يوم (المجموع خلال 30 يومًا ≈ 570، فوق الهدف 510). تحقق أن هذا مطبّق فعليًا بـ`pacing.py`/`planner.py` قبل التفعيل، لا نية موثّقة فقط.
- [ ] **راقب الارتداد أول 3 أيام** فور التفعيل: `GET /admin/overview` يوميًا — `bounces_today` ÷ `sends_today` يجب أن يبقى دون 5%. أي تجاوز → أوقف (`MAIL_LIVE=false`) وشخّص فورًا (غالبًا مشكلة بريد الشركة المستهدفة أو تصنيف إيميل خاطئ).
- [ ] فعّل لعميل واحد أولًا (اشتراك تجريبي)، راقب يومًا كاملًا، ثم وسّع تدريجيًا — لا تفعّل لكل العملاء دفعة واحدة.

## 8. النسخ الاحتياطي والاستعادة

- **نسخ يومي تلقائي:** `deploy/backup.sh` مجدول 03:00 (cron على الخادم) — ينسخ Postgres (masar + n8n) وإعدادات n8n، مشفّرًا بـGPG (passphrase في `/root/.masar-backup-env`، لا يُرفع لـGitHub أبدًا). يحتفظ بآخر 14 يومًا.
- **تشغيل يدوي فوري:** `ops backup-now` عبر Core - Call، أو من بوت الأدمن.
- **الاستعادة:** تحتاج SSH فعليًا (عملية حساسة لا تُترك لأمر ops عام) — فك تشفير النسخة بـGPG بنفس passphrase، ثم `pg_restore`/`psql < dump.sql` حسب صيغة النسخة. اختبر الاستعادة على قاعدة تجريبية منفصلة أولًا، لا مباشرة على الإنتاج.

## 9. إغلاق النظام القديم (n8n Cloud القديم)

لا تُطفئ أي جزء من النظام القديم قبل أن يثبت الجديد نفسه فعليًا: **3 أيام متتالية** يعمل فيها Masar Core دون أي تدخل يدوي طارئ منك (لا `نحتاجك فورا`، لا تعويض ضمان غير متوقع، لا شكوى عميل) **وبعد** أن ينتقل كل عميل حقيقي فعليًا للنظام الجديد (لا عميل نشط متبقٍ على n8n Cloud). فقط عندها أوقف وركفلوهات n8n Cloud القديمة (لا تحذفها فورًا — عطّلها أسبوعًا احتياطًا قبل الحذف النهائي).

## 10. متى تحتاج تدخلًا فوريًا منك

النظام يرسل لك رسالة تبدأ بـ`نحتاجك فورا —` فقط حين: سرّ يجب أن تُدخله أنت، قرار دفع، إطفاء نظام قديم، أو فشل متكرر 3 مرات لنفس البند. أي رسالة أخرى (تقرير يومي مساءً "تقرير مسار اليومي") معلوماتية فقط، لا تتطلب فعلًا فوريًا.
